# Safe Agent Recovery — Stage 1 Design

Status: approved in conversation; written specification awaiting final review

Ledger: REQ-228

Date: 2026-08-28

## Problem

NurProxy already validates nginx and Apache configurations, snapshots files before
an apply, rolls a failed batch back, reports a free-form `last_error`, and builds
copy-paste permission remediation. These mechanisms are disconnected. An operator
can see that `nginx -t` failed, but often cannot tell which file caused it, whether
NurProxy owns that file, whether rollback succeeded, or whether the condition is
safe to repair automatically.

The production incident that motivated this design was a deleted NurProxy TLS
vhost whose certificate had already been removed. The stale vhost made `nginx -t`
fail, validation ran before pruning, and the same failure prevented pruning. One
orphan blocked every desired vhost on the agent. Commit `979f39a` corrected that
specific ordering. This design turns that class of recovery into a systematic,
observable facility.

## Scope

Stage 1 delivers structured diagnosis, safe repair decisions, local snapshots,
verified rollback, a bounded automatic-repair loop, persistence, API exposure,
and an operator-facing recovery panel.

It does not execute systemd, sudoers, package, firewall, ownership, or arbitrary
operator-config changes. Those actions remain diagnosis-only in Stage 1. Stage 2
will add a tightly allowlisted root helper as a separate systemd unit delivered by
the existing `nurproxy-agent` package; it will not introduce another package.

## Safety policy

Automatic repair is enabled by default, globally configurable, and overridable per
agent. A repair may run automatically only when all of these predicates are true:

1. The affected resource is provably NurProxy-owned.
2. The diagnosis has a stable, known error code and one deterministic remedy.
3. Every mutation target is inside a resolved, allowlisted backend or agent-data
   directory after symlink-safe canonicalization.
4. The complete prior state can be snapshotted locally before mutation.
5. A deterministic rollback exists and is tested before the repair type ships.
6. A backend-specific post-check can prove the repaired state valid.
7. No artifact is manual, adopted, drifted, or awaiting operator review.
8. The circuit breaker permits an attempt.

Failure of any predicate changes the result to diagnosis-only. Unknown does not
mean repairable. A filename prefix alone is not ownership proof.

### Ownership classes

- `nurproxy`: the resource is generated by NurProxy and matches either the current
  desired target or the backend's managed-file marker plus its resolved layout.
- `operator`: the artifact is adopted, manual, drifted, or lacks NurProxy's marker.
- `system`: permissions, service manager, package, firewall, port, binary, or other
  host state outside NurProxy's artifact contract.
- `unknown`: evidence is insufficient or contradictory.

Only `nurproxy` is eligible for automatic repair.

## Architecture

### Structured diagnostic model

The agent converts backend errors into a common diagnostic before updating health
or sending an apply ACK. The wire and REST representation contains:

```text
Diagnostic {
  id, code, subsystem, severity, ownership,
  summary, evidence, affected_paths,
  resource_fingerprint, proposed_action,
  auto_repair_eligible, hard_change,
  first_seen_at, last_seen_at, occurrences
}
```

`id` is stable for the same agent, code, and resource fingerprint. Evidence is
sanitized and capped at 8 KiB. It may include the relevant configtest excerpt,
file and line, but never certificate keys, tokens, environment values, or whole
configuration files.

Initial stable codes are:

- `managed_orphan_config`
- `managed_stale_temp`
- `managed_cert_file_missing`
- `managed_runtime_key_missing`
- `managed_runtime_key_mismatch`
- `generated_config_invalid`
- `operator_config_invalid`
- `permission_denied`
- `systemd_sandbox_denied`
- `proxy_reload_failed`
- `proxy_not_running`
- `port_conflict`
- `proxy_binary_missing`
- `unknown_proxy_error`

Backend parsers remain pure. nginx extends its existing `in <file>:<line>` parser;
Apache extends its existing `on line N of <file>` parser. A shared classifier maps
parsed evidence plus artifact metadata to ownership, stable code, and action.

### Recovery coordinator

A focused agent package owns repair eligibility and execution. It consumes a
diagnostic, the authoritative desired-set metadata, backend capabilities, and the
effective settings. It produces either a diagnosis-only result or a typed repair
plan. Plans contain action identifiers and validated paths, never shell commands.

The Stage 1 action allowlist is:

- `prune_managed_orphan`
- `remove_managed_temp`
- `rematerialize_cert_bundle`
- `rematerialize_runtime_key`
- `restore_last_live_artifact`

The coordinator serializes execution per agent. It creates a recovery directory
under the agent data directory, snapshots files and symlink state, writes a small
manifest, performs the typed action, validates the full proxy configuration,
reloads when needed, re-reads managed checksums, and records the result. A failed
mutation or post-check restores the snapshot and validates the restored state.
If rollback validation also fails, the operation becomes `rollback_failed`, health
stays red, and no further automatic attempt is permitted.

Snapshots are retained for seven days and capped at the newest 20 operations.
Pruning never removes a snapshot referenced by an active operation.

### Repair state machine

```text
detected
  -> diagnosis_only
  -> planned -> snapshotted -> applying -> validating -> succeeded
                                      \-> rolling_back -> rolled_back
                                                        \-> rollback_failed
  -> suppressed
```

Every transition is idempotent. A process restart resumes only validation or
rollback from the on-disk manifest; it never blindly repeats a mutation whose
completion is unknown.

### Circuit breaker

The breaker key is `(agent, action, resource_fingerprint)`. Three failed or
rolled-back attempts within 15 minutes open the breaker for one hour. A successful
repair clears it. While open, matching failures are coalesced into the existing
diagnostic and no reload or audit storm occurs. Operators may retry manually from
the UI, but the same eligibility and snapshot rules still apply.

### Orchestrator persistence and transport

The orchestrator persists diagnostics and repair operations in additive SQLite
migrations. A repair operation stores agent, diagnostic, typed action, risk,
request source (`automatic` or `user`), state, timestamps, step summaries,
snapshot reference, validation outcome, rollback outcome, and sanitized error.

Agent-originated automatic repairs are reported over authenticated agent REST
endpoints. User-requested Stage 1 repairs are persisted first and delivered as a
typed event over the existing outbound agent stream, preserving operation behind
NAT. Progress and completion return through authenticated ACK endpoints. Repeated
requests with the same operation ID are idempotent.

No browser connects directly to an agent. No raw command or unrestricted path is
accepted by the orchestrator or agent.

### Settings

- Global `safe_auto_repair`, default `true`.
- Per-agent nullable override: inherit, enabled, or disabled.
- The effective value is returned with agent details and shown in the dashboard.
- Disabling affects new automatic attempts immediately; it never cancels an
  operation already in rollback.
- Manual Stage 1 repairs remain available when automatic repair is disabled.

## Repair catalogue

| Condition | Stage 1 behavior |
|---|---|
| Managed vhost absent from authoritative desired set | Snapshot, prune config/symlink/sidecar/cert, validate, reload, rollback on failure |
| Managed `.nurproxy-tmp` or abandoned stage file | Remove after proving no active operation owns it; validate if backend-visible |
| Referenced cert/key file missing but the pushed valid bundle exists | Re-materialize from the bundle, validate, reload |
| Plain runtime key missing or mismatched but encrypted source decrypts and matches the certificate | Re-materialize the runtime key, validate, reload |
| New generated config fails validation | Existing atomic apply restores the last live artifact; record structured diagnosis, do not invent a rewrite |
| Operator/manual/adopted config fails validation | Diagnose file and line; no automatic mutation |
| Permission, systemd sandbox, package, port, or binary problem | Diagnose and show proposed hard action; execution deferred to Stage 2 |
| Missing cert with no valid central bundle | Diagnose; normal issuance/retry policy remains authoritative |
| Unknown or ambiguous error | Preserve raw sanitized evidence; no automatic mutation |

## UI and API

The existing agent detail view gains a `Diagnosis & recovery` panel rather than a
new administration area. It shows:

- plain-language cause, stable code, severity, ownership, file and line;
- relevant evidence and affected paths;
- whether automatic repair is eligible and why it did or did not run;
- live operation progress;
- snapshot, validation, rollback, and final outcome;
- repair history and circuit-breaker state;
- global and per-agent automatic-repair controls.

Safe manual actions use one `Repair` confirmation. Stage 1 hard/system actions are
visible but disabled with an explanation that privileged execution arrives with
the same-package helper. Stage 2 will enable `Repair` followed by a second `Sure?`
confirmation for hard actions.

The API exposes list/detail endpoints for diagnostics and operations, the effective
setting, and an authenticated request endpoint for eligible typed Stage 1 actions.
API errors state which safety predicate rejected execution. Existing free-form
`last_error` remains for compatibility and is derived from the highest-priority
active diagnostic.

## Observability

Audit events cover detection, suppression, plan creation, snapshot, each typed
step, validation, success, rollback, and rollback failure. Duplicate detections
increment an occurrence count rather than append unbounded audit entries.

Prometheus adds bounded-cardinality counters by code/action/outcome and gauges for
active diagnostics, open circuit breakers, and repairs in progress. Hostnames,
paths, and operation IDs are not metric labels.

## Security constraints

- Resolve configured backend layouts first; reject paths outside them and the
  agent data directory.
- Use `lstat`/directory-FD-safe operations so a symlink swap cannot redirect a
  repair outside an allowlisted tree.
- Verify NurProxy markers and database/desired-state ownership; never infer
  ownership solely from a basename.
- Never accept shell, command, environment, unit, user, group, or arbitrary path
  strings from the browser.
- Redact secrets and cap stored evidence.
- Require normal authenticated admin access and CSRF protections for manual repair.
- Permit one live repair per agent and make operation IDs single-use.
- Keep the main agent's existing systemd sandbox. Stage 1 grants no new privilege.

## Testing

1. Table-driven unit tests cover every error code, ownership class, eligibility
   predicate, state transition, breaker transition, and evidence-redaction rule.
2. Negative security tests cover traversal, symlink swaps, deceptive filenames,
   manual/drifted artifacts, injected commands, replayed IDs, and concurrent ops.
3. Real nginx and Apache integration tests inject missing certs, stale managed
   vhosts, invalid generated config, invalid operator config, reload failure, agent
   crash, and rollback failure.
4. API tests cover authentication, persistence, idempotency, settings inheritance,
   progress ACKs, and compatibility of `last_error`.
5. Browser E2E covers diagnosis rendering, automatic-repair history, settings,
   manual `Repair`, progress, rollback, and disabled hard actions.
6. Production canary deploys to `orax`, exercises a temporary Cloudflare/ACME
   domain through create, controlled fault, healing, HTTPS, and delete, then rolls
   to `durox`. Traffic and `nginx -t` are monitored throughout.

## Rollout and rollback

The database migration is additive and old agents ignore new stream event types.
The orchestrator ships first with execution disabled for agents lacking the new
capability bit. Agents then roll out `orax` before `durox`. Automatic repair starts
enabled only when the agent advertises Stage 1 capability and all safety predicates
hold.

Binary backups, database backup, agent data snapshots, configtest, service health,
and live traffic checks gate each production step. A failed canary restores the
previous binary and leaves `safe_auto_repair=false` until reviewed.

## Future stages

Stage 2 reuses the diagnostic, operation, UI, state machine, audit, and rollback
contracts. The existing agent package will additionally install a socket-activated
root helper using the same binary in helper mode. It accepts only compiled action
types for systemd, permissions, packages, firewall, and service restart. The main
agent receives no broader privilege.

Stage 3 expands the catalogue from real incidents and test fixtures. It does not
weaken the eligibility predicates or introduce a general remote shell.

## Acceptance summary

Stage 1 is complete when REQ-228's six criteria are evidenced by automated tests
and an `orax` then `durox` production canary, with no traffic loss, no mutation of
operator-owned state, bounded retries, and a demonstrated automatic rollback.
